# MLflow

This directory deploys MLflow as Kubeflow's multi-user experiment tracking
service. MLflow workspaces map to Profile namespaces carrying the
`app.kubernetes.io/part-of=kubeflow-profile` label. The Kubernetes authorization
plugin evaluates each request against the caller's Profile role bindings.

## Layout

- `values-kubeflow.yaml` is the reviewed input to the canonical MLflow Helm chart.
- `upstream/base` is generated by `scripts/synchronize-mlflow-manifests.sh` and
  must not be edited directly.
- `overlays/kubeflow` adds Profile-aggregated view, edit, and administrator roles
  and limits network ingress to Profile namespaces and `istio-system`. The
  published chart does not yet expose configurable ingress sources, so this
  platform-specific restriction is a Kustomize patch, not an upstream edit.

The deployment uses the `kubeflow` namespace, the `/mlflow` URL prefix, the
`kubeflow-gateway` Istio gateway, and the identity headers supplied by the
platform OAuth2-Proxy. The MLflow ServiceAccount can discover Profile namespaces
and submit Kubernetes SubjectAccessReviews. Callers receive MLflow permissions
through the standard Kubeflow Profile roles. The MLflow Service is a ClusterIP
and direct Service access is not an end-user path: requests must enter through
the authenticated Kubeflow gateway, which supplies the trusted identity headers.
NetworkPolicy controls reachability; the Istio AuthorizationPolicy admits only
the gateway ServiceAccount; MLflow then evaluates the normalized user and groups
through SubjectAccessReview. These are separate security checks.

A `default-editor` ServiceAccount token can be used as a bearer token through
the gateway when OAuth2-Proxy uses the platform's Kubernetes-token overlay (for
example `m2m-dex-and-kind`). Istio supplies `kubeflow-userid` and
`kubeflow-groups`; the client must not supply identity headers. The default
Dex-only overlay does not enable Kubernetes bearer tokens. Direct-token Service
access in the standalone chart uses `self_subject_access_review`, unlike this
gateway-only `subject_access_review` deployment.

## Installation

**Release blocker:** the currently published `v1.6.0` image fails during
authorization endpoint compilation and does not become ready. The source-image
validation below is a preview, not a repair of that published image. Before
merging this default integration, publish a corrected canonical image, update
`values-kubeflow.yaml`, regenerate the base through the synchronization script,
and validate that published image without the CI source-image override.

Install the Kubeflow namespace, Profile controller, Istio, and OAuth2-Proxy
before MLflow. Then run:

```bash
kustomize build applications/mlflow/overlays/kubeflow | kubectl apply -f -
kubectl wait --for=condition=Available deployment/mlflow \
  --namespace kubeflow --timeout=300s
```

Open `/mlflow` through the Kubeflow gateway or use the **MLflow Experiments**
entry in the Central Dashboard.

Replace the example public domains in `mlflow.allowedHosts` with the actual
Kubeflow gateway domains before synchronization. Localhost port-forward access
is included by the chart; do not replace the allowlist with `*`.

## Validation

With the platform installed and the gateway forwarded to `localhost:8080`:

```bash
python3 tests/mlflow_manifests_test.py
python3 tests/mlflow_gateway_harness_test.py
python3 tests/mlflow_install_test.py
./tests/mlflow_test.sh kubeflow-user-example-com
```

The full integration workflow currently builds the production Dockerfile from
[`kubeflow/mlflow-integration` revision `d3e895d`](https://github.com/kubeflow/mlflow-integration/commit/d3e895dbc120e51f7696f44a4fa54cacbde8ff39),
which installs the checked-out plugin and its declared MLflow dependency range.
It loads that immutable-revision-tagged image into Kind and passes
`MLFLOW_TEST_IMAGE` to `tests/mlflow_install.sh`. A temporary Kustomize overlay
selects the preloaded image with `imagePullPolicy: Never`; generated manifests
remain unchanged. Without that variable, the installer uses the declared release
image. Failed rollouts report Pod details and current and previous container logs.

The live test creates a temporary second Profile through the Profile controller,
uses real ServiceAccount tokens, and checks gateway access, filtered discovery,
editor writes, viewer reads and denied writes, bidirectional cross-Profile
isolation, and resistance to user-header spoofing. It deletes the Profile and
soft-deletes its experiments on exit. Successful requests without client-supplied
identity headers exercise gateway normalization and MLflow SubjectAccessReview;
the cluster-free harness tests do not establish runtime validation.

The full integration workflow runs this test after gateway startup and includes
MLflow in `tests/metrics-server_resource_table.py`. CPU and memory remain
unmeasured until a full-distribution run supplies actual values.

The integration preserves the MLflow operator's `kubernetes` workspace provider,
`kubernetes-auth` entry point, `mlflow.kubeflow.org` virtual resources, and
name-scoped `mlflow-artifact-connection` Secret access. OpenShift-specific TLS,
operator-managed database migrations, and namespace reconciliation remain
operator responsibilities, not features of this distribution overlay.

## Storage

The example profile uses a 2 GiB persistent volume with SQLite metadata and
file-based artifacts. This is suitable for a single-replica evaluation
deployment. Before production use, replace both values with shared services:

- set `mlflow.backendStoreUriFrom` to a Secret containing a PostgreSQL or MySQL URI;
- set `mlflow.artifactsDestination` to S3, Google Cloud Storage, Azure Blob
  Storage, or another shared artifact store;
- disable local storage after both stores are remote; and
- configure the corresponding credentials through `envFrom` or workload identity.

Change `applications/mlflow/values-kubeflow.yaml`, then rerun the synchronization
script. Do not patch the generated base by hand.

## Synchronize

The synchronization script checks out an immutable revision of
`kubeflow/mlflow-integration`, renders its canonical chart with the Kubeflow
values, and validates the generated Kustomize base:

```bash
KUBEFLOW_SYNCHRONIZE_NO_COMMIT=true \
  ./scripts/synchronize-mlflow-manifests.sh
python3 tests/mlflow_manifests_test.py
```

When updating MLflow, change the full `COMMIT` value in the synchronization
script and the image tag in `values-kubeflow.yaml` together, regenerate the
base, and review the rendered resource difference.
Use Helm 4, matching the synchronization workflow (currently 4.2.2).

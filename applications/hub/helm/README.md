# Hub model registry Helm chart

Installs the distribution's `applications/hub/overlays/model-registry` platform
baseline for the Hub version recorded as `appVersion` in [Chart.yaml](Chart.yaml).
The registry and catalog are independent, simultaneous
releases, with distinct resources and namespaces. This chart creates no Namespace
or custom resource definition.

## Installation

Use Helm 4. Install the Kubeflow foundation, Istio and its gateway, authentication
and Profile Controller first. The registry requires the existing
`kubeflow-user-example-com` Profile namespace; the catalog requires `kubeflow`.
The registry also requires a working default StorageClass.

Create a private values file with a unique database password. Keep it outside
Git and reuse it for every upgrade. Registry passwords must contain only URI-unreserved
characters (letters, digits, `.`, `_`, `~`, `-`): the source Deployment embeds
the password directly into its PostgreSQL connection URI. The schema rejects
URI delimiters and percent escapes instead of allowing a broken connection. Do not use `ci/values-platform.yaml` for an
installation: it contains the public upstream demo credentials solely to compare
the exact Kustomize baseline. The chart refuses an empty or placeholder password.

```sh
umask 077
python3 - <<'PYTHON' > /path/to/private-registry-values.yaml
import secrets
print("database:")
print("  password: " + secrets.token_urlsafe(32))
PYTHON
helm lint applications/hub/helm -n kubeflow-user-example-com -f /path/to/private-registry-values.yaml
helm upgrade --install hub-model-registry applications/hub/helm \
  -n kubeflow-user-example-com -f /path/to/private-registry-values.yaml --wait --timeout 5m
```

The release namespace is fixed to match the distribution's routes, policies and
resource references. Arbitrary namespaces, images and storage layouts are not
part of this initial platform chart. The only hoisted resources are the source
credential Secrets: `database.password` is required; the database username comes
from the generated source. Catalog additionally accepts `huggingFaceApiKey`
(empty by default). Images and configuration remain source-controlled payloads.

## Upgrade, rollback and uninstall

The registry owns PVC `metadata-postgres`. Ordinary `helm uninstall` deletes that PVC and can destroy its database, according to the StorageClass reclaim policy. Export and verify a database backup before uninstalling. The Profile and its namespace are external and survive.

Credentials are supplied values and never generated by the templates. Changing a
Secret does not rotate a password inside an existing PostgreSQL data directory.
Coordinate database-side rotation and workload restarts separately; changing a
password value alone is not a supported rotation procedure. No checksum rollout
annotation is added, because it would change the default Kustomize pod template.

A same-version Helm upgrade and rollback must preserve credentials and data while
its database Pod remains running. Cross-version schema rollback is not promised:
consult the pinned Hub release's database compatibility and verify a backup first.

```sh
helm history hub-model-registry -n kubeflow-user-example-com
# Only use a compatible revision and the same credential values.
helm rollback hub-model-registry REVISION -n kubeflow-user-example-com --wait --timeout 5m
# Destructive database operation; see storage behavior above.
helm uninstall hub-model-registry -n kubeflow-user-example-com --wait --timeout 5m
```

The legacy chart under `experimental/helm/charts/hub` and its 14 scenarios remain
available. This platform chart does not claim an automatic migration of its
values or ownership. Do not install both charts over the same resources. Plan
backups, resource ownership and the legacy values conversion before migrating;
there is no blanket `--take-ownership` or force-conflicts procedure.

## Maintenance and validation

Payloads use the shared manifest engine and are loaded literally through
`.Files.Get`; no generated YAML is evaluated as a Helm template. Regenerate and
verify that the second run changes no files instead of hand-editing generated files.

```sh
KUBEFLOW_SYNCHRONIZE_NO_COMMIT=true ./scripts/synchronize-hub-manifests.sh
python3 scripts/generate-hub-registry-helm-manifests.py --check
python3 tests/run_helm_kustomize_comparison.py hub-model-registry --all-scenarios
python3 tests/helm_release_size.py hub-model-registry
python3 tests/hub_helm_chart_test.py
```

The Helm full-integration workflow replaces only the two Hub installation steps;
the Kustomize workflow retains its original installers. Existing API and registry
authorization tests continue. `tests/hub_helm_lifecycle_test.sh` additionally
exercises same-version unchanged/changed upgrades, rollback, stable Secrets,
SQL sentinels, registry PVC identity and independent destructive uninstall/reinstall.
Run it only in a disposable environment with both private values files. These
lifecycle gates must pass before claiming the chart ready; local rendering tests
alone provide no runtime or cross-version migration evidence.
